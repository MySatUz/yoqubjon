## 1. Что на самом деле тормозит (краткий диагноз)

Лагов не один источник, а четыре независимых, и они бьют по разным сценариям:

**1. Экзамен «залипает» при вводе.** Три компонента (`SplitScreen`, `TopNav`, `BottomNav`) подписаны на zustand-стор **без селектора**. В zustand 5 `setState` всегда создаёт новую ссылку на state — даже когда экшен вернул `{}`. Поэтому тик таймера раз в секунду перерисовывает всё дерево экзамена, а на каждой перерисовке заново парсится вся математика KaTeX (`renderError={() => ...}` — новое замыкание, ломающее `useMemo` внутри react-katex) и синхронно пишется весь стейт в localStorage. Та же цепочка выполняется на **каждый нажатый символ**. Пользователь печатает в момент, когда основной поток и так занят секундным тиком — отсюда лаг ввода.

**2. Белый экран при входе в дашборд.** `src/app/dashboard/layout.tsx` делает `await auth()` + запрос в БД. Так как `cacheComponents` выключен, `loading.tsx` **физически не может** показаться — доки Next 16 описывают это прямо (`layout.md:316-328`). Все четыре написанных `loading.tsx` на входе в раздел — мёртвый код.

**3. Секунда пустого лендинга.** Все LCP-элементы главной отрисованы с `opacity-0` + `animation-delay`. Chrome не засчитывает LCP для `opacity: 0`, поэтому метрика сдвинута на `delay + 0.7s` ≈ 800–1100 мс — при том что HTML статически пререндерен и уже пришёл. Плюс на каждой странице preload-ится шрифт Lora, который **нигде не используется** (69% веса шрифтов — мёртвый груз), и render-blocking KaTeX CSS на страницах без формул.

**4. Админка захлёбывается на объёме.** `/admin/payments` подписывает **120 URL в Supabase отдельными HTTPS-запросами** на каждый рендер, показывая при этом одну ссылку. `/admin/sections/[category]` тянет всю историю попыток без `take` и агрегирует лидерборд в JS. Списки на 1000 записей рендерятся без виртуализации и переrenders на каждый символ поиска.

**Чего в проекте НЕТ (проверено, не тратить время):** N+1 запросов в БД; критически недостающих индексов; загрузки всех вопросов ради счётчика; base64-чтения файлов в память; раздутого `globals.css`; проблем с barrel-импортом `lucide-react` (он уже в дефолтном `optimizePackageImports` Next 16); `AdminForm` как узкого места по ререндерам (491 строка — но поля неконтролируемые).

## 2. Методическое предупреждение: мерить только на прод-сборке

Значительная часть наблюдаемых «лагов» в `next dev` — артефакты дев-режима, а не баги приложения:

- `next dev` компилирует маршруты по требованию — первый заход на любой маршрут всегда медленный (`local-development.md:13`);
- **prefetch в дев-режиме не работает вообще** («Automatic prefetching runs only in production») — значит задачи P1-3 на dev-сервере оценивать нельзя;
- нет минификации — замеры размеров JS в дев-режиме бессмысленны;
- Windows + антивирус: перед замерами добавить `C:\Projects\MYSAT` и `node_modules` в исключения Windows Defender.

Все замеры — только через:

```bash
npm run build
```

```bash
npm start
```

## 5. Разрешение противоречий между аудиторами

Оркестратор проверил спорные места. Эти решения имеют приоритет над текстом отдельных отчётов.

### 5.1. Prefetch: аудиторы B и E предложили противоположное

- **B** требует убрать `prefetch={false}` из `ShellNav` (пункты меню всегда во вьюпорте — отключать нечем оправдать).
- **E** требует добавить `prefetch={false}` в `PracticeCatalog` и приводит `ShellNav` как эталон.

Оба правы в своей части, потому что случаи разные. **Единая политика:**

| Ситуация | Что ставить | Почему |
|---|---|---|
| 3–4 постоянно видимых пункта навигации (`ShellNav`, `AdminSectionHub`) | **ничего** (дефолт `auto`) | для динамического роута дефолт префетчит только оболочку до `loading.js` — дёшево, а `loading.tsx` у этих маршрутов есть |
| Карточки тестов (`PracticeCatalog`) | **убрать `prefetch`** (сейчас `true`) | `prefetch` = полный RSC-payload `/exam/[id]` со всеми вопросами, и это самый тяжёлый маршрут (806 KB) — на каждую карточку |
| Списки в сотни ссылок (юзеры, секции, тесты) | **оставить `prefetch={false}`** | иначе шторм префетчей |

Итог: правило «всегда дефолт, кроме списков в сотни ссылок». Ручной `router.prefetch()` на `onMouseEnter` убрать везде — на тач-устройствах он не срабатывает и лишь маскирует проблему.

### 5.2. Проходят ли картинки лендинга через proxy — утверждение B-2 завышено

B-2 оценил matcher как critical, считая, что `/images/hard-questions-hero.png` идёт через proxy. Проверено: картинка отдаётся через `<Image>`, то есть браузер запрашивает `/_next/image?url=%2Fimages%2F...`, а этот путь matcher **исключает**. Через proxy реально проходят: `/` (лендинг), `robots.txt`, `sitemap.xml`, любые будущие прямые ссылки на `public/`.

**Решение:** задача P1-1 остаётся, но её ценность — в отвязке от Prisma/bcrypt (размер бандла, холодный старт) и в исключении лендинга, а не в «статике». Severity понижен critical → high.

### 5.3. «loading.tsx есть, значит белого экрана нет» — неверно

Аудитор A отметил наличие `loading.tsx` как смягчающий фактор. B доказал по докам, что при `await` в `layout.tsx` фолбэк не рендерится вообще. **Приоритет у B:** пока не сделан P0-6, наличие `loading.tsx` ничего не даёт.

### 5.4. `AdminForm` — не узкое место

Гипотеза (491 строка ⇒ ререндеры на каждый символ) **не подтвердилась**: почти все поля неконтролируемые (`defaultValue` + `FormData`). Реальная проблема файла — сценарий загрузки картинок (P1-19). Не тратить время на рефакторинг ререндеров формы.

### 5.5. `refresh()` из `next/cache` — проверено, существует

Рекомендация D заменить связку `revalidatePath` + `router.refresh()` подтверждена: `refresh()` есть в Next 16 и вызывается **только внутри Server Action** (`docs/01-app/03-api-reference/04-functions/refresh.md`). Это кросс-доменная задача (см. §6).

## 7. Индексы БД

Критически недостающих индексов **нет** — все FK и горячие фильтры покрыты. Изменения дают микроскопический выигрыш и делаются в P2, отдельной миграцией, после `EXPLAIN` на реальных данных.

Добавить: `Result @@index([userId, testId])` · `ManualPaymentRequest @@index([status, createdAt(sort: Desc)])` · `SectionAccess @@index([createdAt])`.

Удалить как избыточные (дорожат самый горячий INSERT — сабмит экзамена): `Result @@index([userId])` (покрыт композитом `[userId, createdAt]`) · `Subscription @@index([userId])` (покрыт `[userId, isActive, expiresAt]`) · `Payment @@index([transactionId])` (дублирует `@unique`).

Перед удалением обязательно: `EXPLAIN` на `WHERE "userId" = $1` и проверка `pg_stat_user_indexes.idx_scan`.

### Найдено попутно (за рамками перфа)

1. **`npm start` ломает аутентификацию.** next-auth v5 бросает `UntrustedHost`, защищённые страницы отдают «Unauthorized». В `.env` задан `NEXTAUTH_URL` (имя из v4), v5 ожидает `AUTH_URL` или `AUTH_TRUST_HOST=true`. В `next dev` не воспроизводится.
2. **Часть действий админа не обновляла UI вообще** — выдача роли админа, одобрение и отклонение платежа требовали ручного F5. Исправлено вместе с X-3.
3. **`collection.maxAttempts` на дашборде и в профиле всегда падал в дефолт** — inline-`select` не запрашивал это поле. Исправилось при переходе на общий кешированный ридер. Ничего его не читает, поведение не менялось.

### Поправки к самому плану, выявленные при исполнении

- **`unstable_cache` работает и в сегментах с `force-dynamic`.** Тезис из аудита B (и из §4 этого плана) неверен — проверено по исходнику `next/dist/server/web/spec-extension/unstable-cache.js` в 16.2.6. Снимать `force-dynamic` не требуется.
- **Через proxy картинки лендинга не проходили.** Оценка B-2 завышена: `<Image>` отдаёт их через `/_next/image`, который matcher исключал и раньше. Ценность задачи — в размере бандла, а не в статике.
- **`priority` на hero-картинке убран, а не дополнен `sizes`.** `preload` генерируется без атрибута `media`, поэтому телефон скачал бы скрытую картинку независимо от `sizes`.

### Волна 4 — C-7 (предрендер математики на сервере)

Реализовано **без миграции БД**, вопреки исходному предложению аудита. Замер на самом большом реальном тесте (46 вопросов, 386 формул) показал, что хранение HTML в схеме даёт ровно тот же выигрыш на клиенте, но добавляет риск рассинхрона HTML с текстом вопроса при редактировании. Вместо этого — рендер на сервере при запросе + `unstable_cache` по тесту с тегом `test-questions-${testId}`, инвалидируемым в `uploadTest`, `updateQuestion`, `updateTestDetails`, `deleteTest`.

| Клиентских чанков с KaTeX | 1 (293 202 B) | **0** |

## 11. Волна 5 — остаток P2 и устойчивость сдачи

### Устойчивость сдачи экзамена

Найдено при живой проверке: JWT-сессия переживает удаление пользователя из БД, и сдача падала с **500** (`P2003: Result_userId_fkey`). Теперь отдаётся **401** с внятным текстом, а клиент отправляет на `/login` с `callbackUrl` вместо того, чтобы оставлять студента на мёртвой странице. Проверено вживую: `POST /api/exam/submit` → `401 {"error":"Your account is no longer available. Please sign in again."}`.

Попутно (A-10) убрано дублирующее чтение `User`: та же строка теперь обслуживает и проверку существования, и admin-флаг, и email для проверки доступа к секции. **Сдача платного теста: 10 запросов в 5 стадий → 9 запросов в 2 стадии** (−3 round-trip'а). Транзакция с advisory-lock не тронута.

Клиент дополнительно перестал падать в ветку «проверьте соединение» на не-JSON ответах прокси.

### Индексы: две рекомендации аудита опровергнуты

Проведён `EXPLAIN (ANALYZE, BUFFERS)` и снята статистика `pg_stat_user_indexes` на живой базе. К базе **ничего не применялось**.

| Индекс | Данные | Вердикт |
|---|---|---|
| **+** `Result([userId, testId])` | `BitmapAnd` двух индексов вместо одного | делать |
| **~** `ManualPaymentRequest([status, createdAt DESC])` | своп бесплатный, эффект на 8 строках неизмерим | делать |
| **−** `Payment([transactionId])` | истинный дубль `@unique`, `idx_scan = 0` | делать |
| **+** `SectionAccess([createdAt])` | Seq Scan остаётся даже при `enable_seqscan=off` | **не делать** — вернуться к ~10k строк |
| **−** `Result([userId])` | **`idx_scan = 2969`**, используется для Index Only Scan | **не делать** — посылка аудита опровергнута |
| **−** `Subscription([userId])` | **`idx_scan = 212`** против **0** у композита | **не делать** — статистика обратна аудиту |

`prisma/schema.prisma` обновлена тремя обоснованными изменениями. SQL — в `prisma/manual-migrations/20260817_index_tuning.sql`, вне `prisma/migrations/`, чтобы `migrate deploy` не подхватил его автоматически (`CREATE INDEX CONCURRENTLY` не работает внутри транзакции, в которую Prisma оборачивает миграции).

```bash
psql "$DATABASE_URL" -f prisma/manual-migrations/20260817_index_tuning.sql
```

До применения схема опережает базу — это намеренно и описано в самом файле вместе с процедурой снятия дрифта.
